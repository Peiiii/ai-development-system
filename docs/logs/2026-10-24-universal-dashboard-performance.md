## 实验环境和口径

Apple M4、16 GiB、macOS arm64、Node v22.23.2，使用本机已有 Git，没有新增依赖。1/20/100 个临时项目，每项目 83 篇可读 Markdown，其中 80 篇约 4 KiB；同时存在 node_modules 文档与超过 1 MiB 的文档。规模组均带安装标记，避免把旧版漏掉普通项目的「快」当性能优势。另一个普通项目组删除安装标记后验证原型显式目录可用，旧版发现仍为 0。

每组各三次独立 Node 进程，交替执行顺序，**OS 文件缓存未清空**。这里的轻量数据耗时不包含 CLI 模块加载、读取登记配置、工程根发现、HTTP、浏览器加载或绘制；登记路径由夹具直接提供，项目名称列表在该计时段外构造。不是冷盘结果，也不是产品 P95。真实当前仓库只读对照另列；没有扫描其它私人项目。

计时含文件 API 包装与采样开销；API 计数不是所有系统调用，RSS 为绝对采样值，可能漏掉瞬时峰值。`eager-start` 包含全部索引及快照序列化；`staged-start` 只准备轻量概况，分页序列化在单项目索引计时后进行。因此分阶段首屏值不能宣传为完成相同全局工作的提速倍数。

## 规模实验（最终规模轮的中位数）

| 项目 / 可读文档 | 现有全量后端准备 | 原型轻量概况 | 后续选中项目完整索引 |
| --- | ---: | ---: | ---: |
| 1 / 83 | 151 ms | 3.7 ms | 112 ms |
| 20 / 1,660 | 1,684 ms | 2.3 ms | 121 ms |
| 100 / 8,300 | 12,184 ms | 4.7 ms | 123 ms |

100 项目现有启动观测范围为 10,660–15,344 ms，原型轻量概况 2.6–11.1 ms，选中项目索引 107–297 ms；这体现系统调度和文件 I/O 波动，不能忽略最大观测值。前一轮同机 100 项目全量中位数 8.85 秒，也说明不能只用一次最快结果决策。

更稳定的结构性证据是工作量：100 项目全量路径读取约 32.55 MiB、35,806 次被观测文件 API 调用；轻量概况只读 66 字节工程清单、3 次调用，后续所选项目索引约 333 KiB、351 次调用。其它项目文档不进入当前项目启动/索引路径。登记列表自身仍随项目数线性增长，最终 UI/API 需要分页，不能宣称所有规模都 O(1)。

100 项目全量快照约 4.06 MiB；原型概况（含 100 个目录项名称）约 12.8 KiB，当前项目 40 条无正文资料页约 19.7 KiB。现有全量启动采样 RSS 中位数约 184 MiB；原型索引所选项目后约 56 MiB。没有证明实际生产服务和浏览器采用新协议后也会得到相同内存数值。

## 增量与边界正确性

以下断言通过，失败会使程序非零退出：

- 缓存再次访问：0 次文件 API 调用，0 字节正文读取。
- 无变化刷新：83 份解析结果复用，0 字节正文读取；仍重新枚举并校验元数据，不用根目录 mtime 假装知道嵌套变化。
- 修改 1 篇、新增 1 篇、删除 1 篇：仅 2 次正文 read，共 4,312 字节，复用 81 篇；新增可见、修改生效、删除消失，总数保持 83。
- 文件/正文/时间预算耗尽明确返回部分结果；25 项预算不超枚举上限，部分结果不能覆盖旧完整 83 篇快照。
- node_modules 与 >1 MiB 文档未进入可读索引。
- 首屏 0 个 Git 子进程；只有选中项目主动读取时执行 status/log 两条只读命令。子进程超时终止机制通过临时 Node 进程验证；不宣称任意大型 Git 仓库均已覆盖。

## 复审发现与优化

1. **不要只停读取、继续枚举剩余大目录。** 压力夹具额外加入 700 篇约 33 KiB 文档，首版达到 8 MiB 正文预算后仍对剩余文件 lstat；观察到 798 次 lstat。已加预算终止信号，立即退出所有目录迭代层，复测须小于 400 次，且读取字节不得超过 8 MiB。对特别大的文件夹用 opendir 限制实际枚举，避免 readdir 一次分配全部目录项。
2. **采样开销不能当作产品空闲消耗。** 每 5 ms 的 RSS/延迟采样在一秒 idle 中自身产生约 25 ms CPU，不能据此判断 <1% 空闲目标是否通过。追加没有周期采样器的一秒 idle 对照；它只能验证原型，无生产服务驻留 CPU 结论。
3. **单项目完整索引还未证明无回退。** 规模轮当前真实仓库旧路径 316 ms，原型索引 358 ms，且原型多读根 AGENTS（108 篇 vs 107 篇）。前轮旧路径 292 ms/原型 223 ms，存在明显波动。首屏拆分已证明可以减少等待，但单项目全量总成本需要正式实现后多次同机回归，不能以首屏数字掩盖这里的未达标风险。
4. **时间预算是软上限。** 100 项目夹具所选项目单次索引观察到 297 ms，真实项目有 358 ms，不能宣称所有索引在 250 ms 内结束。原型允许 500 ms，压力字节预算实验显式放宽到 10 秒来单独测字节上限；正式实现要分片、局部返回，并验证正在等待的文件系统操作不能被用户态硬中断的边界。

因此通过的是「先切断全量成本链、按项目索引、指纹复用」这一方案方向及上述正确性实验；**不是生产上线性能门已通过**。

12:33 复测正常退出，预算优化生效：大项目达到约 8 MiB 正文上限即停止，lstat 从 798 次降至 334 次（约减少 58%），观测文件 API 总调用从 1,767 降至 1,299；耗时仍有波动，不宣称同等比例变快。32 项枚举上限严格保持 32，原完整缓存保留验证通过。不带采样器的一秒 idle CPU 仅 0.278 ms（约 0.028%，仅原型短样本）。真实仓库本轮旧路径 279 ms，原型轻量概况 3.7 ms、完整索引 252 ms、无变更刷新 63 ms；与前轮相反的耗时关系再次说明需要正式回归样本而非单次上线结论。规模 JSON 保留预算终止优化前的完整 1/20/100 结果，followup JSON 对应优化后的单项目、压力预算和当前仓库复测。
