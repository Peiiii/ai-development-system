# DevWeave 开发效果测评 MVP

状态：MVP 设计；实际效果以运行报告为准。

## 目标与边界

用户希望只给 AI 一个相对模糊的开发目标，由 AI 自主调查、确定必要边界、实现、验证并交付可靠结果；用户不承担日常 Review 和催促。测评首先检验这种委托在一个固定开发任务中是否成立，同时记录时间、Token、失败与人为介入。单个任务只能证明该任务上的表现，不能推出普遍收益。

测评能力归本仓库，不进入接入项目的 CI 或运行时。接入项目继续只需安装、使用和升级。MVP 不增加新规则、阶段或代理。

## 主链路

1. 从仓库内固定 fixture 建立两个新的 Git 工作目录。两边的产品上下文、起始代码、任务提示、Codex CLI 版本、模型、推理设置、运行上限和外部环境相同。
2. treatment 通过正式安装器接入当前 DevWeave；baseline 不安装。两个目录在 Codex 开始前各自形成初始提交。Codex 使用 `codex exec --json`、GPT-6 Luna、非交互模式，在目录内独立完成同一模糊任务。
3. 独立 grader 位于工作目录外，运行后检查用户路径及异常边界；记录通过项、补丁、Token、耗时和退出原因。主要完成判定同时要求 Codex 正常结束并交付最终回复、grader 全部通过；即使截止时代码通过测试，也不能把超时记成完整交付。超时、鉴权失败与测试失败分别报告，不合并为低质量分数。
4. 先运行一对样本检查流程。随后同任务至少三对、交错执行以减弱时间和服务状态影响；用于对外宣称一般效果前加入未参与调优的任务，并公开任务、环境、原始计数与失败案例。

当前固定任务是本地 task inbox。用户提示只要求“把它完善到可以安心用于日常记录，自己判断缺口并交付”；仓库 README 给出已有 CLI 合同。初始独立 grader 检查跨进程持久化、完成状态、无效输入、不存在的 ID、损坏状态保护及帮助入口。2026-09-28 首轮运行后发现并发写入丢任务的漏检，作为事后发现单独报告，并把并发添加加入后续冻结的第六项验收；不能将新检查伪称为原始预设分数。这样模糊的是目标与必要工作判断，验收合同仍可复验。

## 执行环境与认证

首选可信远程 Linux 主机：Codex CLI 用本人 ChatGPT 订阅登录，独立普通用户持有凭据；每次运行新工作目录，`workspace-write` sandbox，串行执行，不把凭据放进仓库、日志或结果包。`auth.json` 只在可信主机保存，Codex 自身维护刷新。GitHub Actions 可在以后触发私有自托管 runner；临时托管 runner 需要安全存取刷新后的认证文件，MVP 不引入这层状态管理。现有 CLIProxyAPI 仅供 localhost，不作为远程传输层。

成本界限：默认每组仅一次、每轮十分钟、顺序运行；扩大重复次数需要显式参数。订阅额度是实际消耗，JSON 事件的 Token 用量是可比量，不换算成不存在的 API 账单。失败后不自动无限重试。

## 验收

- 一条命令可在任何装有 Node 20+、Git 和已登录 Codex CLI 的可信机器运行一对样本；不依赖 NextClaw。
- 结果包含每轮环境身份、DevWeave 版本、测试明细、退出原因、时长与 Token；grader 不出现在代理工作目录。
- fixture 原版不能通过独立验收，证明 grader 至少能区分未交付与已交付。
- 能在远程机器真实运行 Luna 一对样本并取回报告，或明确给出远程阻塞证据；不把本机 dry run 说成远程效果。

非目标：此 MVP 不评估大型产品交付的全部能力，不建排行榜、仪表盘、自动发布或接入项目检查。后续任务集与真实用户委托逐步补足外部效度。
