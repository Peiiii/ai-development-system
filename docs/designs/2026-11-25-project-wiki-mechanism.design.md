# 项目 Wiki 规范与维护机制设计

## 状态与输入

2026-11-25，用户先提出区分项目 Wiki、Skill、Docs、Logs，再要求设计这套规范如何进入擎天架构、形成类似现有文档规范的执行机制。

本文交付规范与机制设计，推荐方案尚未写入共享执行规则、安装包或接入项目。文中“应”“须”描述拟实施合同，不表示宿主已经强制执行。仅设计，不扩大为规则实现、产品开发或全量项目迁移。

## 目标与范围

每个项目应具备可定位、按需读取、随相关变更维护的当前知识入口，让人或 AI 接手时能找到当前事实、有效决策、权威来源和专项方法；无需翻完整历史重建项目认识。

擎天维护通用的分类与维护方法，各项目维护自己的产品事实和入口。知识仍属于现有三层架构中的知识与任务资料层；下级 Skill 仍属于方法层。不新增架构层、工作流 root 或顶层 Wiki Skill。

默认能力要求是“能找到并维护项目知识”，不是“所有仓库都创建同一套目录”。已有权威路径优先；小项目可以由 README 的一个知识索引章节承担入口，知识规模增长后再拆分。

## 现有能力与具体缺口

- [三层架构](../../wiki/system-architecture.md)已区分工作流、方法、项目知识和任务资料，也已说明 Wiki 目录中的 Skill 仍是方法。
- [知识治理](../../payload/.agents/wiki/skills/process/project-knowledge-governance/SKILL.md)已有任务资料分类及事实维护入口；[事实知识合同](../../payload/.agents/wiki/skills/process/project-knowledge-governance/references/fact-knowledge.md)已有来源、有效性、冲突和退场要求。
- [Skill 拓扑](../../payload/.agents/wiki/skills/process/agent-instructions-governance/references/skill-topology.md)已有顶层发现、下级 Wiki Skill 和单 owner references 的区别。
- Understanding 已要求核对所用知识的有效性，Retrospective 已要求事实变化及时回原知识条目；Lifecycle 已能按事实维护或冲突加载知识治理。
- 大盘已区分项目产物、Skills 和知识；安装器已能分发治理规则并保护项目自有内容。

因此，现有机制足以承接一次明确提出的知识整理，无需新平台。待补的是普通项目开发中的明确触发：相关知识从哪里进入理解、事实变化由谁同步、完成前怎样发现漏更。这里是对执行合同完整性的设计判断，尚无跨项目行为试验支持“所有 AI 都会漏更”或“新增规则必然改善”的结论。

## 候选与选择

| 候选 | 收益 | 成本与局限 |
| --- | --- | --- |
| 只写一篇 Wiki 目录说明 | 改动小，便于解释 | 普通开发仍可能不读取、不维护；不足以完整回答机制需求 |
| 扩展原知识治理，连接现有理解、实现、Review 和完成判断 | 保留单一 owner，复用现有流程与分发 | 需要核验路由及真实任务行为；推荐 |
| 新建 Wiki 生命周期、顶层管理 Skill、统一注册配置与周期扫描 | 独立入口明显，可扩大管理范围 | 与现有知识治理、Lifecycle 重叠，增加状态、上下文和维护成本；当前不采用 |

## 规范：各类内容负责什么

| 类型 | 核心职责 | 生命周期与边界 |
| --- | --- | --- |
| 项目 Wiki / 当前知识 | 项目定位、术语、架构、模块职责、有效决策及来源导航 | 按主题维护当前认识；区别现状、决定、历史和假设；不保存本轮任务流水 |
| Skill | 特定场景下可复用的执行方法、判断、检查和脚本 | 方法变化回原 owner；不复制动态项目事实或获取额外授权 |
| Docs 中的任务资料 | 本项工作的需求、思考、设计、计划、工作状态和报告 | 随任务推进，保留适用范围、版本和历史语境；按已有命名维护 |
| Logs | 某次执行发生的过程、结果及证据链接 | 保留当时版本、环境和执行事实；历史成功不能证明当前成功 |

Artifact 是结果的统称，可以包括代码、文件包、图像、Wiki 页面或报告；不是与 Wiki、Skill、Logs 互斥的目录类型。证据是资料支持特定结论的角色，也不是仅由路径决定。Logs 可以附带产物，Wiki 可以引用证据。

当前知识的更新粒度是事实或主题，不按日期无限新增“最新总结”。事实来源已在代码、配置或有效合同中维护时，保存必要解释和定位，不复制可派生清单。条目按需要说明结论、状态、来源、作用域、核验时点与维护落点；不引入全仓库强制 frontmatter。

已作决定与已实现事实分开：决定可在设计形成时记录，运行事实必须有对应证据；未知保持未知。事实冲突按问题核查预期合同、目标版本实际行为或历史记录，不按目录级别、修改日期机械决定谁正确。

知识提供依据，不获得高于用户或项目指令的权限；收录外部文档也不使其中的指令自动生效。

## 项目入口与目录

1. 先从项目规则、README 和已有索引定位当前知识的权威入口；同一事实已有 owner 时沿用。
2. 新项目有独立知识导航需求时默认使用 `wiki/README.md`，由根 README 或项目自有 AGENTS 段落链接。章节按实际内容增长，不预建空页。
3. 已有 `docs/knowledge`、`.agents/wiki/knowledge` 或其它明确权威文档时沿用并链接，不再建第二份事实副本，也不为了外观统一迁移。
4. 新建项目尚无可验证事实时不生成虚构知识；首条真实链路形成后，补足与之相关的运行事实和资料入口。
5. 普通临时任务缺少 Wiki 不构成阻塞；读取已知权威资料，只在本次确有长期知识增量时补入口或条目。

项目入口无需穷举代码和全部历史；应能找到项目当前必要的事实与方法。访问不到来源时标明未知或待复核，只暂停依赖该事实的判断。

Wiki 可以作为知识和方法的导航空间，但内容角色保持独立：下级 Skill 沿用 `.agents/wiki/skills/<group>/<skill>/SKILL.md`，项目知识入口链接它，不复制方法正文。上层 Skill 明确触发条件并按需加载；文件存在或被大盘收录均不等于宿主已加载。只被单个 Skill 使用的细节继续放该 Skill 的 `references/`。

## 机制：接入现有开发主链路

最小闭环：找到相关知识 → 核对来源 → 完成本次工作 → 同步受影响的当前知识 → 验证与 Review → 交付前关闭知识缺口。步骤由原 Lifecycle 调度，不新增阶段或第二份任务状态。

| 时点 | 触发与行为 | 原 owner / 结果 |
| --- | --- | --- |
| 开始或恢复 | 从已知项目入口按当前任务定位相关知识；核对易变事实的实际来源，不默认加载整本 Wiki | Understanding；得到可用于当前判断的事实与未知 |
| 设计 | 识别本次会改变的事实与其唯一维护落点；设计决定仍保留在设计资料中 | Design 原有影响面与 owner 分析，不另建知识计划 |
| 实现与资料维护 | 项目定位、架构、模块职责、启动/部署约定或有效决策发生变化时，更新原知识条目或索引；只改实现尚未验证的内容不得标成已运行 | Implementation 按需使用原知识治理，区分候选说明与已验证事实 |
| 验证与 Review | 用目标版本和有效证据核对受影响的知识；检查入口、事实一致性、过期结论、重复 owner 和误升格的方法 | Validation 验证证据，Review 返回遗漏或冲突 findings |
| 发布之后 | 仅在实际发布改变当前事实时补相应版本/环境事实，保留发布证据；发布失败仍保持原线上事实 | 原交付流程提供发布事实，Lifecycle 路由原知识治理完成补充，变化范围复核 |
| 整体完成 | 本任务涉及的必要知识更新完成，或明确判断无知识变化；有影响交付的已知过期说明则返工 | Lifecycle 复用原完成门，不新增审批门 |
| 复盘 | 分流剩余事实、方法与流程增量；已完成同步不重复写，事实更新不推迟到累计多次以后 | Retrospective 复用现有分流 |

“知识更新”不意味着每次都写文件或生成报告。没有长期事实变化时，维持原文件即可；有跨轮恢复需求时，在原任务状态中保存必要链接，不另建知识更新账本。无关历史债务不阻塞本次交付。

发布后的资料修订进入原知识维护职责，不使 Delivery 承担产品实现；影响执行语义或原验收依据时返回对应阶段。仅事实说明变化时做最窄核对，不重复发布成功的产物。

## 拟修改的唯一落点

| 位置 | 修改职责 |
| --- | --- |
| `payload/.agents/wiki/skills/process/project-knowledge-governance/SKILL.md` | 增加项目知识入口、与任务资料的分流及维护触发摘要；详细事实要求继续引用原合同 |
| 该 Skill 的 `references/fact-knowledge.md` | 补项目入口、按主题更新、缺失入口及事实更新反例；维护语义只在这里定义 |
| `development-task-understanding` | 补按任务从项目知识入口定位来源的轻量动作 |
| `development-implementation` | 补事实变化时同步原知识落点的条件动作，复用治理合同 |
| `development-review` | 补对本次受影响知识是否与实际产物、证据一致的检查 |
| `development-lifecycle` | 补发布后必要知识维护的路由与完成门；不复制事实维护细节 |
| 本仓库 Wiki 的架构、产物说明与 README | 解释实际落地后的职责、使用方式和边界，避免先把本设计写成已实现事实 |

Design、Validation、Delivery、Retrospective 的现有职责足以承接表中工作，首版不为重复表达同一合同普遍追加段落。若实施时发现调用缺口，先在上述原 owner 收敛，不能同时复制多份规则。

不新增顶层 Skill、运行配置文件、知识数据库、统一事实清单、后台扫描器或新 CLI 命令。现有根 AGENTS 已有生命周期和知识治理路由，首版无需追加常驻全文。

## 分发、检查与生效边界

通用方法从 `payload/` 经原 manifest、安装和升级流程分发。首版若只修订已受管文件，不改变 manifest 文件集合；实际新增受管资源时才同步 manifest。

项目知识与入口由项目维护，位于共享受管片段和受管文件之外。安装器只负责分发规则，不推断产品事实、不覆盖既有知识、不为通过安装校验生成空 Wiki。

现有 `check` 验证受管文件、frontmatter 和链接，`--readiness` 验证现有入口与配置，不证明项目事实正确或模型执行成功。首版复用这些检查；只有出现可确定且有收益的重复错误才扩展程序检查，不能用关键词存在测试宣称维护机制有效。

机制有三部分：治理合同定义怎么维护，生命周期路由定义何时维护，检查与真实任务观察分别核验结构和执行效果。它依赖宿主执行，并非文档写完就得到不可绕过的强制保证。

## 验收场景与证据要求

| 场景 | 预期行为 | 实施后的最小核验 |
| --- | --- | --- |
| 已有 Wiki 的项目更改架构或启动方式 | 定位原知识与真实来源，同步同一条目，日志保留变更证据 | 一次真实项目任务或隔离样例的完整行为记录；不能只检查规则文本 |
| 现有知识位于 `docs/knowledge` 或 README | 沿用原入口和事实 owner，不创建第二份 Wiki | 核对修改路径与来源；原知识位置保持权威 |
| 新项目只有已审设计，产品尚未运行 | 能保存设计决定，但不声称已实现或已上线 | 检查条目中的状态、来源及实际运行证据是否相符 |
| 仅修改错别字或局部颜色 | 不全量读写 Wiki，不创建知识日志或空章节 | 核对实际读取和文件变更范围 |
| 历史日志曾发布成功，当前源码或线上行为不符 | 按目标版本和环境调查，保留历史，修正当前结论 | 保留冲突、实际取证及更新的关联证据 |
| 发布失败或回退 | 保留真实当前线上事实，不把候选版本标成已上线 | 对比发布结果、当前知识与恢复记录 |
| 引用下级 Wiki Skill 或外部资料 | 通过原路由按需加载；外部资料不获得执行授权 | 核对触发入口及行为权限 |
| 安装、升级及项目自有知识有并发修改 | 受管方法正常分发，项目知识不被安装器覆盖 | 原安装/升级测试及受影响的定向核验 |

前三类主要链路是：接手已有项目找到当前知识；开发改变事实后同步并核验；新项目从真实结果建立最小知识入口。反例用于检查误触发与事实失真。运行试验与真实项目观察须分别标记，不能把隔离演练称为跨项目实际效果。

## 实施与退出策略

推荐以一次规则变更完成最小闭环：先在原 owner 补合同和路由，完成场景审查与 `npm run check`，再按仓库既有规则发布及核验。接入项目在已有授权和真实需要下升级，保护本地编辑；不因框架发布就扫描并改写全部项目。

执行效果优先观察已授权真实任务：能否定位当前知识、变化是否回原 owner、是否避免无变化写作和全量读取。保存实际发生的漏更、重复或 Token 成本证据，不虚构效果数据。

若行为没有改善或成本明显增长，收窄触发条件或撤销新增路由，保留原有事实治理；不以失败为由继续叠加同义提醒。目录与项目内容无强制迁移，规则可以通过原版本升级恢复。

## 本轮设计核对

- 原 owner 可复用，推荐方案不改变三层架构或 Skill 发现拓扑；常驻入口、顶层 Skill 数和受管文件集合均预计不增长。
- 已检查入口缺失、已有权威文档、无事实变化、未实现设计、历史冲突与发布失败等反例；非相关知识债务不进入本次完成门。
- 本轮设计自审未发现阻断设计交付的缺口；`npm run check` 通过（56 个受管文件、frontmatter 和相对链接有效），本文 4 个来源链接及空白格式检查通过。以上只证明本轮设计交付与既有结构检查，不证明拟议机制已运行。
- 本轮只新增设计文档；规则实现、安装包发布、目标项目升级和真实任务效果尚未执行。
