# 项目知识职责与协作边界设计

## 状态与设计输入

2026-11-25，用户提出每个项目应有知识库，区分 Wiki、Skill、Docs、Logs，并要求设计规范与执行机制。随后明确纠正：不接受把 Wiki 提醒分散补到多个开发阶段，要求职责清晰、解耦，让知识规范的演进集中在自己的维护位置。

本文以完整知识职责和稳定协作边界重写原方案。当前仅交付设计，尚未修改共享规则、安装包或接入项目；以下合同是拟实施行为，不表示宿主已强制执行。

## 架构决定

项目知识由一个完整职责拥有；开发流程通过统一入口使用它。

- **Development Lifecycle** 拥有任务编排、授权边界、返工与整体完成判断，决定何时请求知识能力，消费处理结果。
- **Project Knowledge Governance** 拥有知识入口定位、相关知识读取、来源与有效性核对、增量更新、冲突处理、过期与归档。调用方无需知道 Wiki 的具体组织与维护规则。
- **开发阶段 Skills** 继续负责理解、设计、实现、验证、Review、交付和复盘，按原合同提供任务结果、来源、证据与风险，不各自承担知识治理。
- **项目 Wiki** 承载当前项目知识。它是知识治理维护的内容，不是流程编排者，也不因收录内容而获得执行授权。

知识治理沿用现有 `project-knowledge-governance`，事实细节由其 `references/fact-knowledge.md` 承载。不新增顶层 Wiki Skill、独立知识生命周期、通用插件系统或后台进程。

这里的解耦标准是：目录、条目结构、来源判定、冲突策略或归档规则变化，只修改知识 owner 及其内部材料；只有协作的输入、输出或时机发生真实变化，才修改调用方。解耦允许明确依赖，不要求双方零交互。

## 架构位置与既有能力

[三层架构](../../wiki/system-architecture.md)继续成立：Lifecycle 属于工作流层；[知识治理 Skill](../../payload/.agents/wiki/skills/process/project-knowledge-governance/SKILL.md)和其它 Skills 属于方法层；Wiki、任务约定、工作状态、证据属于知识与任务资料层。

现有[事实知识合同](../../payload/.agents/wiki/skills/process/project-knowledge-governance/references/fact-knowledge.md)已有来源、有效性、冲突、更新和退场要求；现有 Lifecycle 已有知识治理条件路由。现有能力能处理明确提出的知识整理请求，适合直接承接完整知识职责。

本次需要补齐的是统一调用边界和普通开发中的接续方式。缺口不是每个阶段缺一段提醒，也不是缺少新的目录扫描器。当前没有跨项目行为试验，不能提前声称该设计保证模型执行或已经提高维护效果。

## 内容职责

| 内容 | 负责什么 | 如何演进 |
| --- | --- | --- |
| Wiki / 当前知识 | 项目定位、术语、架构、模块职责、当前有效决定及来源索引 | 按主题持续维护当前认识，区分现状、决定、历史与假设 |
| Skill | 某类任务的执行方法、判断、检查和配套资源 | 更新方法 owner；下级 Skill 的发现方式沿原拓扑 |
| Docs 中的任务资料 | 本项工作的需求、思考、设计、计划和推进状态 | 依照任务进展维护，保留适用范围 |
| Logs | 某次实际执行的过程、结果及证据入口 | 保留当时版本、环境与历史语境 |

Artifact 是结果的统称，不与上述内容互斥；证据是资料支持特定结论的角色，也不由目录名保证。Logs 可以附带产物，Wiki 可以引用证据。

知识治理继续拥有其现有的资料分流职责。本文不把 Docs、Logs 的执行记录全部纳入 Wiki，也不另建与现有工作记录 owner 重叠的资料管理器。

## 知识 owner 的完整内部职责

1. **定位**：从项目规则、README 或既有索引找到唯一权威入口，沿用项目实际组织。
2. **提供上下文**：按当前问题选择必要事实与来源；核对版本、环境和有效性；有冲突或未知时明确返回。
3. **核对增量**：对照本次实际结果和原有知识，判断哪些事实变化，哪些只是设计决定、临时状态或重复记录。
4. **维护内容**：更新原条目与索引，避免事实副本；代码、配置或合同已有权威来源时，保存解释与定位，不手抄清单。
5. **校验与退场**：验证修改内容与证据一致、链接可用、范围正确；过时内容修订、替代或归档，不继续作为默认当前结论。

知识 owner 不决定产品要做什么，不重做产品验收，不发布产品，不创建执行授权。它拥有知识正确性的核对责任，产品是否实际运行仍以相应版本、环境与验证证据为依据。

## 统一协作入口

调用方以任务意图请求知识能力，首版只需两个操作语义，不建立新的运行时 API、强制 JSON schema 或状态数据库。

| 操作 | 输入 | 知识 owner 完成的工作 | 返回给调用方 |
| --- | --- | --- | --- |
| 提供任务上下文 | 当前问题与范围、目标版本或环境、已知来源位置 | 定位知识、按需读取、核对相关来源与有效性 | 可用事实与来源、适用范围、冲突和未知 |
| 核对并同步知识 | 本次结果与变化范围、实际产物和证据位置、未完成或未验证项 | 判断知识增量、更新原条目、处理过期内容并核验 | 已处理或无变化、修改位置与依据、仍缺的证据或条件 |

输入复用开发任务已有资料和阶段返回，不能要求各阶段再填一套 Wiki 表格。调用方提供证据位置即可，由知识 owner 定位必要原件，不把所有原始日志复制进调用内容。

这不是两个新模块，也不要求两次模型调用；同一 Agent 可以按职责顺序执行。仅当当前操作确实发生时，才读取治理所需材料。

## 与开发流程的接续

原 Lifecycle 是开发任务与知识治理的唯一编排连接点，各阶段之间仍不相互调用。

1. **需要项目知识时**：任务范围已足够明确、且下一步判断需要项目事实时，Lifecycle 请求“提供任务上下文”，再让当前任务继续。不是在理解目标之前盲读整本 Wiki；简单改动已有充分证据时可不调用。
2. **本次结果稳定时**：Lifecycle 将已有结果、证据与未验证项交给“核对并同步知识”。该操作自己判断是否要更新；完成判断只消费结果，不复制分类和维护细节。
3. **中途事实冲突时**：当前阶段按原合同返回未知、风险或返工依据，Lifecycle 通过同一知识入口核对，随后接续当前任务。不新增每阶段的 Wiki 触发清单。

结果稳定指本次范围内最后一次实际事实变化之后。若范围包含发布，发布结果属于输入；发布失败、回退或部分上线必须保持实际状态。已经完成核对后又有相关变化时，只重新处理受影响范围，不重复成功的发布动作。

知识 owner 返回不足以判断时，Lifecycle 决定只暂停依赖该事实的部分，还是允许带明确未知继续；不能把阻碍本次结果的过期说明写成已同步。无关历史债务不进入本任务完成范围。

开始和收口的两个使用位置都定义在 Lifecycle 的同一协作段落。知识治理不依赖理解、设计或发布阶段的名称，开发阶段不依赖 Wiki 内部目录。

## 项目知识的组织由 owner 封装

新项目需要独立知识导航时，默认入口为 `wiki/README.md`；小项目可由 README 的知识索引章节承载。已有 `docs/knowledge`、`.agents/wiki/knowledge` 或其它明确权威文档时沿用，不建第二份事实副本。

没有可验证内容时不预建空页，不把待实施方案写成运行事实。条目按实际需要说明结论、状态、来源、适用范围和核验时间；不用所有项目统一的元数据表单。

Wiki 可导航到下级 Skill。[原 Skill 拓扑](../../payload/.agents/wiki/skills/process/agent-instructions-governance/references/skill-topology.md)继续拥有发现规则：下级方法沿用 `.agents/wiki/skills/<group>/<skill>/SKILL.md`，由调用入口按需加载；单 owner 细节继续放其 references。知识治理引用方法入口，不复制方法正文或替代指令系统治理。

以上是知识 owner 的内部规范。将来调整这些组织细节，不需要修改 Understanding、Implementation、Validation、Review、Delivery 或 Retrospective。

## 最小实施边界

| 位置 | 一次性建立的职责 |
| --- | --- |
| `project-knowledge-governance/SKILL.md` 及其 `references/fact-knowledge.md` | 完整知识职责、两个操作语义及内部规范；详细事实合同保留在唯一 owner 内 |
| `development-lifecycle/SKILL.md` | 在一处定义请求、接续和完成判断的协作边界，复用已有条件路由 |
| 本次设计及框架架构说明 | 解释责任与依赖；实现完成后再将框架说明更新为当前事实 |

不按阶段逐个追加 Wiki 专属段落。实施时将既有相关条款区分为两类：通用的“事实必须有来源、不能猜测”属于阶段本职，可以保留；知识整理、分流、归档等专属职责归知识 owner，既有复盘只返回候选与依据，由 Lifecycle 按统一入口接续，避免保留两套执行路径。

初次建立明确边界可能需要清理真实重复调用；不承诺机械只改两个文件。验收看完整职责是否集中、后续内部规范能否独立变化，而不是用本次 diff 文件数量冒充解耦。

## 分发与检查

通用合同通过原 `payload/`、manifest、安装和升级流程分发。项目知识和入口归项目维护，安装器不推断事实、不覆盖自有内容、不为通过检查生成空 Wiki。首版复用已受管文件，实际未新增资源时无需扩充 manifest。

原静态检查继续验证受管文件、链接和结构；知识 owner 核验知识内容与证据；实际任务观察验证协作是否执行。这三类证据各自支持对应结论，不能由关键词测试推断模型已经执行。

## 设计验收

| 场景 | 成功标准 |
| --- | --- |
| 修改 Wiki 目录或归档策略 | 只改知识 owner 及其内部资料，开发阶段规则无需跟着调整 |
| 接手已有知识项目 | 统一入口返回有来源的相关上下文，任务不读取全部历史 |
| 架构或启动方式改变 | 结果与证据交给 owner，原知识条目更新且有核验依据 |
| 仅修改错别字或局部样式 | 不强制准备知识上下文；无知识增量时不写文件、表格或日志 |
| 历史成功与当前行为冲突 | owner 区分版本、环境和历史；未知返回调用方，不编造当前结论 |
| 新项目只有设计，或发布失败 | 可以保存决定与失败事实，不写成已运行或已上线 |
| 结果核对后又发生相关变化 | 经同一入口仅核对受影响范围，完成判断消费最新结果 |
| 请求只限于设计或调查 | 同步范围内的实际知识增量，不触发产品实现或发布 |

结构验收可通过职责与依赖检查；行为验收需规则实施后的隔离演练或已授权真实任务记录，两者分别标记。衡量的是上下文是否可用、更新是否准确、无变化是否保持轻量，以及知识规范变化是否局部化。

若失败，优先修知识 owner 或统一调用边界，不把提醒重新分散进各阶段；若无净收益，收窄或撤销新增协作规则。本文设计不要求目录迁移、新配置或后台调度。

## 本轮交付边界

本轮直接重写原设计，移除多阶段分散挂接方案；旧稿由 Git 历史保留，不另建并行设计。共享规则、安装包发布、接入项目升级与真实任务效果均尚未执行。

设计自审已核对职责完整性、统一调用、资料缺失、无变化、发布失败和核对后再次变化等边界，未发现阻断本轮设计交付的缺口。`npm run check` 通过（56 个受管文件），本文 4 个来源链接和 diff 空白检查通过；本轮未修改执行规则，以上检查不构成新机制的行为验证。
