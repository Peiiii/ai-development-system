# 显式 Workflow 入口

## 目标与验收

用户指出大型交付虽然被称为 workflow，却在 workflow 路径中找不到。仅修改架构说明没有交付可发现、可读取的入口。本次在共享 payload 中建立 `.agents/workflows/`，并在官网提供第五个可选择的流程。

- 目录列出 initialization、standard、trivial、bugfix、major-delivery 五个命名入口；安装与升级后同样存在。
- 大型交付的完整流程正文迁至 `workflows/major-delivery.md`；旧 reference 仅兼容链接，不形成两个规则 owner。
- Lifecycle 明确先判断外层交付，再分类当前工作项；仍独占阶段调度、返工和整体完成。风险与授权不变。
- 基础 workflow 文件拥有各自顺序与专属门；阶段方法仍由原 Skills 拥有。大型交付可嵌套四种基础 workflow，子结果回到整体集成与完成检查。
- 官网有独立按钮、流程图和正文链接；桌面和手机均能切换，源文档在线可读取。

## 设计取舍与执行

保留四种基础 `flow` 与 `delivery-mode: major`，不增加互斥的第五个任务类型或第二个 Meta Skill。物理目录表达流程约束，Skill 表达执行方法，Wiki 表达体系事实。初始化的详细附加门仍归原 reference。

先用入口回归检查复现当前目录和按钮缺失，再迁移正文与更新路由、manifest、官网和分发。验证 payload 链接、真实安装、旧版升级、网站交互与包 smoke；检查差异后提交推送。共享 payload 改变需发布新 npm 版本并部署官网，核对远端文件与校验和。面试知识快照随后对齐实际新路径。

## 审查与边界

设计审查：兼容入口不保留重复正文；基础分类顺序、风险门、阶段返回、授权与整体完成门均复用现有 owner。官网静态源副本仅由构建生成。发现性回归与安装实测能证明入口可用，不能证明模型长期执行效果；大型交付继续标为试用。
