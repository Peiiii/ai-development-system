# 可复用 AI 驱动开发体系：独立仓库与项目接入设计

日期：2026-09-24
状态：方案 Review 后修订；首版已实现并完成 NextClaw 接入验证。真实第二项目和其它 Agent 工具仍需后续消费者验证。

## Review 修订（2026-09-24）

原稿有三处会让首版失真：整目录搬运会把阶段 Skill 内的 NextClaw 专项路径带到新项目；根 `AGENTS.md` 强制插入共享段会让 NextClaw 的现有常驻规则重复；以 Git commit 作为唯一版本身份无法校验开发中的 payload。实施按逐文件依赖闭包抽取，共享文件不得链接不存在的项目方法；已有完整常驻规则的项目可选择 `--agents=skip`，锁文件记录该选择；内容摘要是安装与升级的校验身份，Git commit 只作为可选来源信息。其它 Agent 工具和真实第二项目接入仍需后续消费者验证，首版用隔离项目装配及代表性路由场景证明可用性。

## 1. 目标与边界

把 NextClaw 已运行的 AI 开发体系整理为一个可独立演进的权威来源，让其他项目能够安装、使用和升级。迁移首先追求现有有效行为的完整保留；通用化只处理真实的项目耦合，不以缩短文本或重写术语为目标。NextClaw 是第一个接入和回归验证的项目。

一次成功的首版接入应满足：新项目能从目标、设计、实现、验证、Review、交付走通一项真实任务；NextClaw 现有开发任务的路由、授权边界、项目专项方法和渐进加载仍成立；上游更新可被发现、审查并安全应用；项目事实与项目授权不会被分发到其他仓库。

首版以当前 Codex 的 `AGENTS.md` 和 `.agents/skills` 加载方式为目标。其他 Agent 工具的接入留待用真实第二种工具验证后设计。独立仓库暂不承担产品运行时、通用任务平台、自动发布或跨项目知识数据库的职责。

## 2. 已有资产与耦合事实

NextClaw 当前有常驻 `AGENTS.md`、16 个顶层 Skill、24 个下级 Wiki Skill，以及独立的 references、脚本、命令登记和项目知识。现有架构把流程、阶段方法、知识与受控演进分开；这些职责边界应沿用。现状中的 `development-lifecycle` 已使用可复用的三路径流程，但仍引用 `commands/commands.md`、NextClaw worktree 命令和项目发布合同。`development-delivery` 直接路由 NextClaw NPM、Desktop 与主线协调。`AGENTS.md` 混有通用协作边界、产品愿景、项目授权及具体仓库约定。

因此不能按目录整批复制，也不能仅靠替换 `NextClaw` 字样。迁移时逐条判断语义 owner；无法证明通用的条目先留在 NextClaw，由迁移账本标记待判断。原设计与历史日志留在 NextClaw，不因源码迁移而改写历史。

## 3. 选择的主链路

独立仓库保存共享规则、Skill 和可移植检查的唯一上游版本。目标项目保留 Codex 原生目录布局；同步工具把上游管理的文件安装到目标项目，并记录上游版本和文件摘要。项目自己的 `AGENTS.md`、项目 Skill、命令、知识与脚本仍在目标项目维护。

```
独立仓库 payload/.agents/skills/development-*
             │ 版本化同步、差异检查
             ▼
项目仓库 .agents/skills/development-*  ──► Codex 原生发现与按需加载
项目仓库 AGENTS.md + 项目专项 Skill      ──► 项目目标、授权和运行路径
```

同步只改变文件归属和分发方式，不建立第二套 lifecycle。共享 Skill 仍是流程或方法的 owner；项目专项 Skill 只提供项目事实、命令、发布和环境方法。共享方法需要项目事实时，从目标项目的常驻入口或对应项目 Skill 获取，不预设某个项目的路径或命令。

### 方案比较

| 方案 | 结果 | 本次判断 |
| --- | --- | --- |
| 仓库模板复制 | 首次接入简单，后续各项目形成独立副本 | 不满足持续迭代和可审查升级 |
| Git submodule 直接挂载 | 上游版本明确 | Codex 的根 `AGENTS.md`、Skill 发现路径及项目局部内容的装配需要额外机制 |
| 版本化源仓库 + 同步安装 | 目标项目保留原生布局，能固定版本并审查差异 | 作为首版主链路；同步工具保持小而确定 |

## 4. 独立仓库目录设计

以下是**批准后实施的目标结构**；当前磁盘上只存在本设计文件。

```text
ai-development-system/
├── README.md                       # 人类入口、支持范围与接入说明
├── manifest.json                   # 上游管理的逐文件路径，单一映射来源
├── payload/                        # 安装到项目的权威源文件，保留目标相对布局
│   ├── AGENTS.shared.md            # 首次接入时进入目标根 AGENTS.md 的共享段落
│   └── .agents/
│       ├── skills/
│       │   ├── development-lifecycle/
│       │   ├── development-task-understanding/
│       │   ├── development-design/
│       │   ├── development-implementation/
│       │   ├── development-validation/
│       │   ├── development-review/
│       │   ├── development-delivery/
│       │   └── development-retrospective/
│       └── wiki/
│           └── skills/             # 经逐项审定的共享下级方法及其资源
├── bin/
│   └── ai-development-system.mjs   # 计划中的 install / check / upgrade 入口
├── checks/                          # 只依赖上游布局的可移植拓扑检查
├── docs/
│   └── designs/                     # 本设计及后续被批准的架构修订
└── tests/                           # 同步器、链接与代表性接入场景
```

目录随实际迁移增长，不创建空的 `checks/`、`tests/` 或 Skill 占位目录。`payload` 的 `.agents` 相对布局应尽量与目标项目相同，减少 Skill 内链接重写。`manifest.json` 只列共享资产及其安装路径；不列 NextClaw 的产品文件或项目知识。顶层 Skill 是否进入 `payload`，按现有发现门逐项判断，不把 16 个入口视为必须全迁的配额。

### 目标项目接入后的归属

```text
some-project/
├── AGENTS.md                        # 项目 owner；含一段受上游管理的共享常驻文本
├── .agents/
│   ├── skills/development-*/        # 上游管理；本地改动先回上游或显式转项目扩展
│   ├── wiki/skills/...              # 上游管理的共享方法 + 项目自己的专项方法
│   └── ai-development-system.lock.json # 安装版本与逐文件摘要
├── commands/commands.md             # 项目自己的意图宏；需要时才创建
└── docs/...                         # 项目愿景、事实、设计与历史
```

默认接入时，共享常驻文本由同步器维护为 `AGENTS.md` 中有边界标记的一段；标记外始终由项目维护。已有完整常驻规则的项目可以使用 `--agents=skip` 并在本地规则中保留开发流程路由，避免重复 owner；该选择写入 lock，升级时不能静默切换。共享段只放跨项目每轮必需的行为约束。项目愿景、已有授权、分支及发布策略只在项目自己的段落中定义。共享 Skill 不通过复制一份项目版本来覆盖差异；项目特定步骤放在目标项目的专项 Skill 或 reference，并由项目入口按条件路由。

## 5. 迁移账本和“无损”判定

实施前建立逐项迁移账本，记录现有文件或规则片段、当前作用、未来 owner、处理动作、原因和验证场景。处理动作只有：上游迁移、项目保留、拆开两种语义、确认过期后删除。任何删除需要独立证据，不能把“看起来项目化”作为删除理由。

| 资产 | 初步归属 | 判定依据 |
| --- | --- | --- |
| 开发生命周期和通用阶段方法 | 上游主体，拆出项目引用 | 多项目共享任务流程和判断 |
| `AGENTS.md` 的协作与安全边界 | 逐条判断后进入共享常驻段 | 不能携带 NextClaw 的产品愿景与历史授权 |
| `nextclaw-*` Skill、NPM/Desktop/Runtime 发布方法 | NextClaw 项目 | 依赖产品和仓库实际运行合同 |
| `commands/commands.md` | NextClaw 项目 | 宏的语义和授权默认作用于当前项目；上游可保留宏治理方法 |
| `.agents/wiki/knowledge` 和产品文档 | NextClaw 项目 | 动态事实、历史和产品决策属于原项目 |
| 治理脚本 | 逐个判断 | 只搬运不依赖 NextClaw 路径、基线或 package 脚本的检查 |

“无损”不定义为文件字节完全相同，而定义为有效行为有明确归属且在代表性任务中可观察地保持。迁移账本必须覆盖原常驻规则、所有被移动的 Skill、它们的 references、脚本调用及反向链接；每项都能从新入口定位，不留下只能靠历史仓库猜测的合同。

## 6. 安装、升级与冲突

计划中的命令是 `install --target <repo> [--agents=skip]`、`check --target <repo>` 和 `upgrade --target <repo>`。升级以当前本地上游 checkout 的 payload 为新版本；调用者先选择上游 Git revision。`install` 先列出将写入的路径及根 `AGENTS.md` 受管段落，再应用；已有同名文件只有内容相同时才允许接管，其它冲突必须停止。`check` 只读，比较 lock、上游 manifest、受管文件摘要、根入口与相对链接。

`upgrade` 以目标项目锁定的旧上游内容和当前上游内容生成差异。受管文件仍与 lock 摘要一致时可更新；发现本地编辑、文件移走、项目段落边界变化或目标文件被其他 owner 占用时，停止该次升级并报告冲突文件，不覆盖项目内容。冲突由使用者判断回馈上游还是移入项目专项层，解决后再运行检查。写入前检查全部路径；写入异常时恢复本次已写文件，进程崩溃后的恢复依赖目标项目 Git 历史。

锁文件记录上游内容摘要、可用时的 Git commit、manifest 格式版本、每个受管目标文件的摘要，以及共享 `AGENTS.md` 段落模式与摘要。目标项目正常 Git 审查同步结果；锁文件与受管文件一起提交，但同步工具本身不自动 commit、push 或发布。首版只从本地克隆的上游仓库读取，不增加远程更新服务、npm 发布或配置 DSL。

## 7. 实施顺序与验收

1. **盘点与冻结基线**：建立迁移账本和代表性行为场景，记录 NextClaw 当前入口、链接、加载预算、相关脚本及项目 WIP。只读取和分类，不移动文件。
2. **抽取共享源**：先移动语义稳定的开发流程与方法，拆分 `AGENTS.md` 的共享段和项目段；逐个修正上游对 NextClaw 的硬链接。项目专项合同仍由 NextClaw 原 owner 承担。
3. **建立安装与检查**：实现最小 manifest、同步器和 lock；在临时空项目安装，在 NextClaw 上做只读 diff 与冲突演练。
4. **NextClaw 接入**：以受管文件替换已核对的共享副本，保留项目规则与专项 Skill。核查源项目没有丢失任何本任务草稿或已有 WIP；通过后才清理迁移产生的重复 owner。
5. **可移植性验证**：首版在隔离的小项目完成安装、standard/trivial/bugfix 路由走查和一次上游升级；有真实第二项目接入需求时，再按其事实与任务结果复核通用化边界。

最小验收矩阵：

| 场景 | 必须看到的证据 |
| --- | --- |
| 新项目首次安装 | 原生发现入口可用；通用任务可以按阶段闭合；项目愿景与授权由项目自己提供 |
| NextClaw 等价接入 | 产品专项规则可从入口命中；现有 standard/trivial/bugfix、验证、Review 和交付路径不断链 |
| 渐进加载 | 顶层/下级 Skill、references、链接、依赖循环与发现预算检查通过 |
| 上游升级 | 版本和差异清晰；未改的受管文件可更新；本地编辑导致显式冲突且无覆盖 |
| 回退 | 目标项目可通过其 Git 历史恢复上一版受管文件与 lock；同步器不产生隐藏状态 |

检查优先复用 NextClaw 现有 `check:skill-progressive-loading` 的可移植部分；项目依赖的 ratchet、文件组织和发布检查继续由 NextClaw 运行。文档静态检查不能替代真实第二项目使用证据。

## 8. 保留、删除与延后

保留现有流程 owner、阶段边界、渐进加载和项目专项方法的单一归属。迁移闭合后删除 NextClaw 中与上游受管内容重复的本地权威副本，但保留安装后的受管文件，因为 Codex 需要按目标项目原生路径发现它们。延后跨 Agent 适配、远程分发服务、自动回传本地修改、跨项目事实同步和通用发布模板；这些都需要真实消费者或稳定重复证据。

首版采用 Codex 优先、上游版本化同步、根 `AGENTS.md` 可选受管段落和项目专项 Skill 这条主链路。用户已授权按 Review 修订方案并落地；实施仍须验证、复核和保护 NextClaw 其它任务的工作区改动。
