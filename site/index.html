03 / THE DEVELOPMENT FLOW

流程需要展示，但不能只有一条。

lifecycle 根据任务性质选择路径，再把当前环节交给对应 Skill；Wiki 在需要事实和共享知识时进入。

标准任务

有方案空间或较高风险时，先设计与审查，再实现、验证和交付。

  1. 01理解任务
  2. 02方案设计
  3. 03方案 Review
  4. 04开发实现
  5. 05验证测试
  6. 06实现 Review
  7. 07交付
  8. 08复盘

简单改动

局部、可逆、风险低的改动走短路径，仍保留必要的验证和 Review。

  1. 01快速理解
  2. 02修改
  3. 03定向验证
  4. 04轻量 Review
  5. 05交付
  6. 06轻量复盘

问题修复

先确定预期、异常与根因，再按风险决定是否需要独立方案 Review。

  1. 01预期与异常
  2. 02复现与根因
  3. 03修复方案
  4. 04修复实现
  5. 05回归验证
  6. 06Review
  7. 07交付与复盘

这里展示的是路径概要；阶段门和例外条件以 架构 Wiki 指向的 lifecycle Skill 为准。

04 / THE EVOLUTION LOOP

自动进化，从复盘沉淀开始。

体系要随真实开发持续改进。当前机制仍处于早期，主要依靠任务收尾时的复盘，识别值得保留的经验。

01 / WORK

真实任务

观察结果、返工与重复沟通。

02 / REVIEW

复盘筛选

判断是否有可复用的增量。

03 / OWNER

找到归属

分流到流程约束、Skill 或 Wiki。

04 / CHANGE

更新并验证

在正确的上游修改，再检查效果。

CURRENT STATE · EARLY

现在是“复盘驱动”，还不是全自动闭环。

没有可复用增量时不新增规则；发现方法缺口时优先修正原 owner。后续会继续增强问题发现、跨项目验证和更新后的效果反馈。

阅读进化机制 Wiki ↗

05 / BUILT TO EVOLVE

接入之后，还能放心迭代。

目标不是复制一次规则，而是让共享方法拥有持续更新、可审查、可回退的来源。

A

先预览，再写入

安装和升级都支持 dry-run。已有同名文件发生冲突时会停止，不会悄悄覆盖项目内容。

↗
B

每个文件都有版本指纹

锁文件记录安装内容的摘要。check 能发现本地改动，也能识别上游是否有新版本。

◇
C

项目语义仍由项目决定

产品愿景、授权、环境和发布规则留在项目中；共享体系只提供可复用的方法。
